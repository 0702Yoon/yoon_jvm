### 왜 신세대 구세대가 등장했을까?

Young Generation의 설계는 Weak Generational Hypothesis에 기반합니다.

**핵심 가설**:

> "대부분의 객체는 단명(die young)하며, 특정 나이를 넘긴 객체는 오래 살아남는다."
>

**통계적 근거**:

- 대부분의 객체는 생성 직후 곧 가비지가 됨
- 예: 메서드 지역 변수, 임시 버퍼, 반복문 내 생성 객체
- Young 객체 중 90% 이상이 첫 번째 GC에서 수집됨

**최적화 전략**:

```
Young Generation (자주 GC)
- 대부분 죽은 객체 → 빠른 수집
- 비용 = 살아있는 객체 수에 비례
- 살아있는 객체만 복사 → Mark-and-Copy

Old Generation (드물게 GC)
- 대부분 살아있는 객체 → 느린 수집
- 장수 객체만 모아서 관리
- 압축으로 단편화 방지 → Mark-and-Compact

```

결론:

즉 객체는 대부분 일찍 죽는 다. 하지만 특정 나이를 넘긴 객체인 경우에는 거의 잘 안죽더라.

그래서 거의 안죽는 객체는 구세대로 옮겨서, GC를 잘 하지 않도록 하자!

### 2.2 Eden 영역

### Eden Space

**Eden Space의 역할**:

> "Eden Space는 대부분의 객체에 대해 메모리가 초기 할당되는 풀입니다." (Oracle Docs)
>

모든 새로운 객체는 `new` 키워드로 생성될 때 Eden에 할당됩니다

**실제 JVM의 Pointer Bump Allocation**:

Eden 공간은 연속된 메모리 블록이며, 할당은 **Bump the Pointer** 방식을 사용합니다:

**할당 과정**:

1. `alloc_ptr`이 가리키는 위치에 객체 할당
2. `alloc_ptr += object_size` (포인터를 객체 크기만큼 이동)
3. 반환: 이전 `alloc_ptr` 값 (객체 시작 주소)

**장점**:

- **O(1) 시간 복잡도**: 단순 포인터 증가만
- **캐시 친화적**: 연속된 메모리 할당으로 공간 지역성(Spatial Locality) 향상
- **단편화 없음**: GC 후 압축으로 항상 연속된 공간 확보

---

**YoonJVM 구현**:

**eden 역할**: 모든 객체가 처음 생성되는 곳

```java
public boolean isEdenFull() {
    return (double) edenSize / maxSize > 0.7;  // 70% 이상 사용 시
}

```

**full 상태를 70%로 설정한 이유**

- GC의 빈도가 잦은 것이, GC가 걸리는 시간이 오래 걸리는 것보다 좋다.
    - **stop the world**
- OOM(Out of Memory) 방지
- 조기 승격을 막기 위함

### Survivor 영역

**왜 Survivor 공간이 필요한가?**

Survivor 공간이 없다면:

```
Eden 가득 참 -> Minor GC -> 살아남은 객체 모두 Old로 승격
-> Old Generation이 빠르게 가득 찬다.
-> Major GC 빈번 발생!!
```

### Survivor 영역의 역할:

Eden에서 살아남은 객체가 곧바로 Old Generation으로 가지 않고 잠시 머무르는 **준비 구역이**다.

- **목적**: 위에서 언급한 대로 대부분의 객체는 금방 죽기 때문에, Survivor 영역에서 몇 번 더 살려두며 나이를 센다. 여기서 나이가 많은 객체만 Old Generation으로 **승격**시킨다.

### 2. 왜 Survivor가 두 개(S0, S1)일까?: "Copying 알고리즘"

Survivor 영역이 하나라면 메모리 단편화 문제를 피할 수 없습니다.

이를 해결하기 위해 **'복사(Copy)'** 방식을 사용하며, 이를 위해 두 개의 공간이 필요합니다.

[→ Minor GC 페이지에 더 명시되어있다.](https://www.notion.so/Minor-GC-2b4bb23038818059b739f3c3f50ad390?pvs=21)
