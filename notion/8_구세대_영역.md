**구세대**: Old Generation은 Young Generation에서 오랫동안 살아남은 객체들이 저장되는 영역.

### 설계 철학 (Design Philosophy)

Old Generation의 설계는 **높은 생존율**을 전제로 합니다.

- **가설의 적용:** "특정 나이를 넘긴 객체는 어플리케이션 종료 시까지 계속 살아있을 확률이 높다."
- **최적화 전략:**
    - 객체가 거의 죽지 않으므로 **GC를 최대한 늦게 수행**해야 한다.
    - 생존 객체가 많으므로 복사(Copy) 비용이 매우 비싸다. → 제자리에서 정리(Compact)하는 방식이 유리하다.

---

### Old Generation의 구조

Old Generation은 Young Generation과 달리 단일 영역으로 구성된다.

Survivor 영역 존재 (X)

**왜 Survivor 영역이 없을까?** (Copying vs Compaction)

Young Generation은 `Copying` 알고리즘을 사용하지만, Old Generation은 `Mark-and-Compact`를 사용한다.

1. **비용 문제:** Old 영역은 생존율이 90% 이상일 수 있습니다. 살아있는 객체를 모두 다른 곳으로 복사하는 비용(CPU Overhead)이 너무 큽니다.
2. **공간 효율성:** Copying 방식을 쓰려면 `To-Space`처럼 비워둬야 하는 공간이 필요합니다(메모리 50% 낭비). Old 영역은 힙의 가장 큰 부분을 차지하므로, 단일 공간을 꽉 채워 쓰는 것이 효율적입니다.

---

### 객체 할당 방식

Old Generation에 객체가 들어오는 경로는 크게 두 가지입니다.

1. 승격 (Promotion)

Young Generation(Survivor)에서 충분히 나이를 먹은 객체(`age >= threshold`)가 이동해옵니다.

- **YoonJVM 구현**

    ```java
    if (obj.getAge() >= TENURING_THRESHOLD) {
        oldGen.allocate(obj); // Old로 승격
    }
    ```


1. **조기승격**
- 객체 할당시에 신세대의 영역이 가득 찼을 경우
- 나이가 차지 않아도 바로 구세대에 할당된다.

**YoonJVM 구현**

```java
if (obj.getSize() > remainingYoungSpace) {
    oldGen.allocate(obj); // Young 공간 부족 시 바로 Old 할당
}
```

1. **대형 객체 직접 할당 (Pre-tenuring)**

아주 큰 객체(Humongous Object)는 Young 영역을 거치지 않고 바로 Old 영역에 할당됩니다.

- **이유:** 큰 객체를 Eden ↔ Survivor 사이에서 복사하는 비용이 너무 크기 때문입니다.

### 5. GC 임계값 (Threshold)

Full 상태를 80%로 설정한 이유

Young Generation(70%)보다 높게 설정된 이유는 **안전성과 비용의 균형** 때문입니다.

1. **비용 최소화 (Frequency):** Major GC(Full GC)는 전수 조사를 수행하므로 비용이 매우 큽니다. 최대한 늦게 발생하도록 임계값을 높입니다.
2. **승격 실패 방지 (Promotion Failure):** 100%까지 기다리지 않는 이유는, Minor GC 도중 갑자기 넘어오는 승격 객체들을 받아줄 여유 공간이 필요하기 때문입니다.
3. **Concurrent GC 고려:** GC 스레드가 도는 동안에도 애플리케이션 스레드가 객체를 생성할 수 있으므로, 20%의 안전 마진(Safety Margin)을 둡니다.

---

### 6. Remembered Set과의 관계

Old Generation이 정리(GC)될 때, **Remembered Set**도 반드시 갱신되어야 합니다.

- **문제:** Old 객체가 GC되어 사라지거나 메모리 위치가 바뀌면, Remembered Set이 가리키는 정보가 상한 포인터(Stale Entry)가 됩니다.
