## 설계 배경

JVM 시뮬레이터를 구현하면서 가장 먼저 고민한 것은 클래스와 객체의 관계를 어떻게 표현할 것인가였다.

실제 JVM에서는 클래스 파일의 바이너리 구조를 파싱하여 클래스 메타데이터를 생성하고, 이를 기반으로 힙에 객체 인스턴스를 할당한다.

“JVM 밑바닥까지 파헤치기”에 나온 바이너리 구조를 그대로 사용하고 싶었지만 JVM의 핵심 개념을 이해할 수 있도록 단순화하면서도 본질은 유지하는 것에 집중했다.

따라서 클래스 파일의 바이너리 구조를 완전히 구현하기보다는, 클래스와 객체의 관계, 그리고 객체가 메모리에서 어떻게 관리되는지에 초점을 맞췄다.

## JVMClass 설계

### 기본 구조

`JVMClass`는 JVM에서 클래스를 표현하는 핵심 클래스다.

실제 JVM의 클래스 메타데이터를 단순화한 형태로 구현했다.

```java
public class JVMClass {
public static final int MAGIC_NUMBER = 0xCAFEBABE;
public static final int DEFAULT_SIZE = 4;
private final int magic;              // 매직넘버 (0xCAFEBABE)
private final int minorVersion;        // 클래스 파일의 부 버전
private final int majorVersion;        // 클래스 파일의 주 버전
private final String className;        // 클래스명
private final List<Field> fields;     // 필드 목록
}
```

### 주요 필드 설명

1. **매직넘버 (Magic Number)**
    - 실제 JVM 클래스 파일의 첫 4바이트는 항상 `0xCAFEBABE`로 시작한다.
    - 이를 통해 클래스 파일인지 검증할 수 있다.
    - `isValidMagicNumber()` 메서드로 유효성 검증이 가능하다.
2. **버전 정보**
    - `majorVersion`과 `minorVersion`으로 클래스 파일 버전을 관리한다.
    - `ClassFileVersion` enum을 통해 JDK 버전별로 정의되어 있다.
    - `isValidFileVersion()` 메서드로 호환성 검증이 가능하다.
    - 낮은 Major 버전으로 컴파일된 클래스 파일은 더 높은 Major 버전을 가진 JVM에서는 작동하지만, 더 높은 Major 버전으로 컴파일된 클래스 파일은 낮은 Major 버전을 가진 JVM에서는 작동하지 않는다.
3. **필드 목록**
    - 클래스가 가진 필드들을 `List<Field>`로 관리한다.
    - 각 필드는 `Field` record로 표현되며, 필드명과 타입 정보를 담는다.

### 상속을 통한 확장

새로운 클래스를 만들 때는 `JVMClass`를 상속받아 구현하도록 설계했다.

```java
public class SumClass extends JVMClass {
	public SumClass(ClassFileVersion classFileVersion) {
		super("Sum", classFileVersion,
		List.of(new Field("Integer", "result")));
	}
}
```

- 클래스명, 버전, 필드를 명확하게 정의할 수 있다.
- 각 클래스의 특성을 쉽게 표현할 수 있다.
- 코드의 가독성과 유지보수성이 향상된다.

## JVMObject 설계

### 기본 구조

`JVMObject`는 JVM 힙에 할당되는 객체 인스턴스를 표현한다. 실제 JVM 객체의 구조를 단순화하면서도, GC를 위한 필수 정보는 모두 포함했다.

```java
public class JVMObject {
	public static final int OBJECT_HEADER_SIZE = 16;
	private final int id;                      // 객체 고유 ID
	private final JVMClass type;               // 객체 타입 (클래스)
	private int size;                          // 객체 크기 (바이트)
	private boolean marked;                    // GC 마킹 플래그
	private int age;                           // 객체의 나이 (GC 생존 횟수)
	private List<JVMObject> references;       // 참조하는 다른 객체들
	private List<Field> fields;                // 실제 데이터
}
```

### 주요 필드 설명

1. **객체 고유 ID**
    - 각 객체를 식별하기 위한 고유 번호
2. **객체 타입 (JVMClass)**
    - 이 객체가 어떤 클래스의 인스턴스인지 나타냄
    - 클래스와 객체의 관계를 명확하게 표현
3. **객체 크기**
    - 메모리에서 차지하는 바이트 수
    - 클래스 크기 + 객체 헤더 크기로 계산됨
4. **GC 관련 필드**
    - `marked`: GC로부터 도달 가능한 객체인지 표시
        - 도달이 가능하다면, GC로부터 생존한다.
    - `age`: GC를 몇 번 생존했는지 카운트 (Old Generation 승격 기준)
    - `references`: 이 객체가 참조하는 다른 객체들의 목록
5. **실제 데이터**
    - `fields`: 객체의 실제 필드 값들

**도메인 주도 설계(DDD)의 원칙에 따라, 클래스는 객체를 생성할 책임을 가진다.**

```java
public JVMObject toJVMObject(int objectId) {
	int totalSize = this.getClassSize() + JVMObject.OBJECT_HEADER_SIZE;
	return new JVMObject(objectId, this, totalSize, new ArrayList<>(this.fields));
}
```

### GC 알고리즘

이 프로젝트는 **Mark-and-Copy GC 알고리즘**을 사용한다.

이 알고리즘은 살아있는 객체를 다른 영역으로 복사하는 방식이므로, 객체 복사 기능이 필수다.

```java
public JVMObject copy() {
	JVMObject copied = new JVMObject([this.id](http://this.id/), this.type, this.size, this.fields);
	copied.age = this.age;
	copied.marked = false;
	copied.references = new ArrayList<>(this.references);
	return copied;
}
```

복사 시 주의할 점:

- 나이(age)는 유지되어야 한다 (Old Generation 승격 기준)
- 마킹 플래그는 초기화한다
- 참조 관계도 함께 복사해야 한다

## 아쉬운 점과 향후 개선 방향

### 클래스 파일 바이너리 구조 미구현

원래는 **클래스 파일의 바이너리 구조**를 완전히 구현하고 싶었다. 이를 위해 다음과 같은 준비를 했다:

- ``AccessFlags``: 클래스 접근 플래그 (public, final 등)
- ``ConstantPoolTag``: 상수 풀 태그 타입들

하지만 이를 완전히 구현하려면:

1. 클래스 파일 파서 구현

2. 바이트코드 해석기 구현

3. 상수 풀 관리 시스템 구현

이 모든 것이 필요했고, 이는 **어셈블러/컴파일러 구현으**로 프로젝트의 초점이 바뀔 수 있었다.

### 향후 개선 가능한 부분

1. 클래스 파일 파서 추가

- 실제 `.class` 파일을 읽어서 `JVMClass`로 변환

- 상수 풀, 메서드 정보 등 추가

- 필드 타입별 실제 크기 계산

2. **메서드 정보 추가**

- 클래스에 메서드 정보 포함

- 바이트코드 실행 (현재는 미구현)

---

## **결론**

JVMClass와 JVMObject의 설계는 **단순하면서도 본질적인 JVM의 동작 원리**를 이해할 수 있도록 구성했다.

특히 **클래스와 객체의 관계**를 명확하게 표현하고, **DDD 원칙에 따라 클래스가 객체를 생성하는 책임**을 가지도록 설계한 것이 핵심이다.

실제 JVM의 모든 기능을 구현하지는 않았지만, GC 알고리즘을 이해하고 메모리 관리의 원리를 학습하는 데는 충분한 구조를 제공한다고 생각한다.
